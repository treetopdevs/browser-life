## Problem and chosen slice

PR89 built `Dockerfile.site` on a Linux runner and tested the packaged image as deployed (`.github/workflows/site-image.yml`, `tools/test/site-image.test.ts`, decisions D10–D18). Backlog D17 says that closed the site-image gap and **not** coordinator-image verification. `Dockerfile.coordinator` (Elixir release, Deno discovery validator cached against `deploy/discovery-validator.lock`, non-root user, `/data` and `/data-discovery`) has never been built or run in CI. Three past failures came from exactly this layer and were found only on a real host: the release default `data-discovery` resolving to the read-only `/app` (crash loop), the validator cache/lock closure, and volume ownership. Only unit-level `mix test` and the source-tree `tests/deno/coordinator_integration.ts` cover the coordinator today.

Slice: build the actual coordinator image on a Linux runner, start it the way `compose.dokploy.yaml` does (default `CMD`, no source mounted, deployed environment and named volumes, synthetic secrets generated per run), prove it serves and authenticates, prove the production startup checks in `apps/coordinator/config/runtime.exs` and `Coordinator.Discovery.init/1` refuse bad configuration, and prove the gate notices a damaged image with two canaries. Same shape and bar as PR89, reusing its patterns.

## Grounding (what the code really does)

- Prod boot (`runtime.exs`, `config_env() == :prod`, release is built `MIX_ENV=prod`): `BL_ADMIN_TOKEN` unset or `""` raises `BL_ADMIN_TOKEN must be set in production` (first check); `SECRET_KEY_BASE` unset raises `environment variable SECRET_KEY_BASE is missing`; `BL_CORS_ORIGINS` entries that are not whole `https://host[:port]` origins raise `BL_CORS_ORIGINS: "<o>" is not allowed in production` (so `*` and `http://…` are refused; unset or `""` yields the empty list, and `config/prod.exs` also sets `cors_origins: []`); `BL_MAX_ISLANDS`, `BL_ISLAND_JOINS_PER_ADDRESS`, `BL_LEASE_MS`, `BL_DISCOVERY_LEASE_MS` raise `<NAME>: "<raw>" is not a positive whole number`; `BL_GARDEN_SCHEDULING` other than on/off raises `BL_GARDEN_SCHEDULING must be on or off`. Blank values (as Compose passes for the optional variables) mean "unset".
- `BL_DISCOVERY_VALIDATOR` is split on single spaces into `config :coordinator, discovery_validator`; the controller appends `--manifest --case --initial --attempt` and runs it.
- `Coordinator.Application.start/2` runs `ConfigCheck.check!/0`, then children in order Queue (`/data`, `mkdir_p`) then `Coordinator.Discovery`. `Discovery.init/1` raises `discovery data dir … overlaps the registered queue's …` when either directory equals or lies inside the other (real paths), which fails the application start and halts the release non-zero.
- `config/prod.exs`: `force_ssl` with `rewrite_on: [:x_forwarded_proto]`, excluding hosts `localhost` and `127.0.0.1`. A request whose `Host` is `cadence.garden` without `X-Forwarded-Proto: https` gets a redirect; with it, 200 plus HSTS. `127.0.0.1` Host (what the test's published port sends) is never redirected.
- `GET /api/public/status`: public, `cache-control: no-store`, JSON with `counts`, `activeIslands`, `deviceTypes`, `updatedAt` only (cold-cache 503 + `Retry-After: 1` possible, so readiness polls). `GET /api/status`: `CoordinatorWeb.Auth.require_admin`; configured token required, `Bearer` secure-compare, else `401 {"error":"admin authentication required"}`; `allow_local_admin` is dev/test only, so loopback inside the container gets no free pass.
- Discovery plane: `POST /api/discovery/workers` needs `Bearer <BL_DISCOVERY_JOIN_TOKEN>` (valid body: lowercase `physicalHostId` and `label`, 64-hex `sourceClosureDigest`); `GET /api/discovery/status` is admin only; wrong or missing token is `401 {"error":"unauthorized"}`. **Finding (no change proposed):** with the join token *unset*, `require_join` admits only `loopback?(conn.remote_ip)`, and `runtime.exs` does not refuse that; the only guard is Compose's `${BL_DISCOVERY_JOIN_TOKEN:?…}`. `loopback?/1` matches `{127,_,_,_}` and `{0,0,0,0,0,0,0,1}` only, while the release binds `::` (dual-stack), where an IPv4 client reaches Plug as an IPv4-mapped tuple that neither clause matches. So whether an in-container IPv4 request is admitted without a token is **not established**: probably 401 over `127.0.0.1`, 200 only via `[::1]`. The gate tests the Compose guard statically (C4) and only *records* the in-container results in the control (see below).
- `compose.dokploy.yaml` coordinator service: no `ports`, `restart: unless-stopped`, `stop_grace_period: 75s`, volumes `coordinator_data:/data` and `discovery_data:/data-discovery`, environment `PHX_SERVER`, `PHX_HOST`, `PORT`, `BL_GARDEN_SCHEDULING=off`, `BL_DATA_DIR`, `BL_DISCOVERY_DATA_DIR`, the three required secrets, and five optional variables passed as empty strings.
- Image: `USER coordinator`, `HOME=/app`, `ENV PHX_SERVER=true PORT=4000 BL_DATA_DIR=/data BL_DISCOVERY_DATA_DIR=/data-discovery BL_DISCOVERY_VALIDATOR=…` (deno `--cached-only --lock=… --frozen`), `CMD ["/app/bin/coordinator","start"]`, `EXPOSE 4000`. `tools/discovery.ts check-attempt` with non-JSON manifest/case files prints `{"valid":false,"errors":["manifest or case is not JSON"],"canonical":null}` and exits 0 after the whole static module graph has loaded.

No coordinator Elixir change is needed for any check below. If a check shows the image cannot boot in CI (for example an IPv6-only `::` bind failing in a container with IPv6 disabled), that is a deployment finding to report, not something to paper over; a runtime change would stop this slice.

## Design (decisions)

**C1. Sibling workflow, not another job.** Add `.github/workflows/coordinator-image.yml`; leave `site-image.yml` and `site-image.test.ts` untouched. Reasons: each job gets its own runner anyway, so a second job in the same file shares only a header; the coordinator build (Hex deps, Elixir compile, Deno cache, several minutes and two extra registries) must neither slow nor mask the reviewed site check; separate check name, concurrency group, scratch directory and cleanup label; and `site-image.test.ts` live cases cannot be re-run locally (no daemon here), so refactoring it into a shared helper would change a proven gate without evidence. The duplicated boilerplate (checkout, setup-node, pnpm) is about 30 lines; extracting shared helpers is a recorded follow-up once both gates have run green. Triggers: `pull_request`, `push` to `main`, `workflow_dispatch` (so the first runs can be started by hand), no path filter (the image closure covers `apps/coordinator`, `packages`, `tools`, `vendor`, `deno.json`, the lock, both Dockerfile inputs and compose). The check must not be made a required status until it has been green on a hosted run. Same authority: `permissions: contents: read`, `persist-credentials: false`, the same pinned `actions/checkout` (`3d3c42e5…`, v7.0.1) and `actions/setup-node` (`949feb24…`, v7.1.0) SHAs, Node 22 and pnpm 10.14.0, `ubuntu-24.04`, `timeout-minutes: 35`, concurrency group `coordinator-image-${{ pr number || ref }}` cancelling only on pull requests. No secrets, no registry login, no push, no build cache action.

**C2. Build once, test by image ID.** `docker build --pull --file Dockerfile.coordinator --iidfile "$BL_SCRATCH/coordinator.iid" --tag bl-coordinator-image:$RUN --label bl.coordinator-image.ci=$RUN .`; validate the iidfile as `^sha256:[0-9a-f]{64}$`; the test accepts only that ID (a tag is refused). The tag exists only so canaries can build `FROM` it (C7). Log best-effort `RepoDigests` for `elixir:1.18.4-otp-27`, `elixir:1.18.4-otp-27-slim`, `denoland/deno:bin-2.9.7` as warnings. Hex and Deno registry downloads happen at build time; an upstream outage fails the job loudly and is rerun by hand, no retry loop.

**C3. The deployed environment is derived, not copied.** The test runs `docker compose --env-file /dev/null -f compose.dokploy.yaml config --format json` with three freshly generated synthetic secrets (`randomBytes(64)` hex for `SECRET_KEY_BASE`, two distinct 32-byte values for `BL_ADMIN_TOKEN` and `BL_DISCOVERY_JOIN_TOKEN`) and starts the image with exactly that `services.coordinator.environment` (including the blank optional variables), no `command`, no mounts other than two labelled **named volumes** at `/data` and `/data-discovery` (so Docker’s copy-up of the image’s `coordinator`-owned directories is exercised as in deployment). Every `docker run` uses `--pull=never`, `--restart no`, no `--init`, and the default bridge with labelled containers (no custom network: nothing else attaches, all probes use the published port or `docker exec`). Stop uses the compose `stop_grace_period` (75 s), read from the derived config. The only deviation from deployment is publishing `127.0.0.1::4000`; the image itself is asserted to declare only `4000/tcp`.

Secret handling (enforced, not asserted): secrets are passed as `-e NAME` inheriting from the spawned process environment (never `-e NAME=value` in argv); each is announced with `::add-mask::` when generated in CI; checks use a boolean helper (`expect(containsAny(text, secrets)).toBe(false)`; for container logs `scanOutput(raw, secrets)`, which decides `leaked` on the raw text and returns the redacted text only for printing) with a fixed message naming which secret, never its value, so Vitest diffs and the failure-report `cat` cannot echo one; compose config output is never printed; `docker inspect` is used only with narrow `--format` fields (never whole `Env`); log dumps are redacted. The redactor and helper are covered in `ci-verify.test.ts`.

**C4. Static checks that run without Docker or an image** (so they run locally and in `pnpm test`): `docker compose config` with each of the three secrets removed in turn exits non-zero and names that variable (the join-token guard is the only enforcement, see Grounding). The "no `ports`" assertion already lives in `tools/test/deployment-config.test.ts` and is reused, not duplicated. These sit outside the `skipIf` like that file, guarded by `hasCompose`; `BL_REQUIRE_COORDINATOR_IMAGE=1` makes a missing Compose fail.

**C5. Behaviour checked against the started image** (describe "the coordinator image, started as deployed"; at least 12 tests so the report check can require a floor). Probes run with `docker exec -e DENO_DIR=/tmp/deno-probe …` except test 9, so only test 9 depends on the image’s Deno cache.
1. Ready: poll `GET /api/public/status` (tolerating the cold-cache 503) until 200 within 60 s; the container is still running (primary evidence); logs contain none of the markers `Application coordinator exited`, `CRASH REPORT`, `Config provider`, `eacces`.
2. Public status: 200, JSON, `cache-control: no-store`, has `counts`, `activeIslands`, `deviceTypes`, `updatedAt`, and has no `experiments`/island fields.
3. Admin auth: `/api/status` with no token, a wrong token and a `Basic` header is 401 `admin authentication required`; with the generated admin token it is 200 JSON containing `limits` and `capabilityNeeds`; the join token is not an admin credential; no body contains a generated secret (boolean helper).
4. Join token required even from inside the container (name: `requires the discovery join token even from inside the container`; no loopback exemption is claimed or excluded): in-container `deno eval` `fetch` does `POST http://127.0.0.1:4000/api/discovery/workers` with a valid body (lowercase `physicalHostId` and `label`, 64-hex `sourceClosureDigest`) and no `Authorization`, expecting 401 `{"error":"unauthorized"}`; a wrong token also 401; the same POST with the real join token is 200 (positive control, so the probe discriminates). Admin routes are not used for this claim (an admin token being configured makes `allow_local_admin` irrelevant there); `allow_local_admin` is proven off only by test 8. The in-container join also creates the worker that tests 7 and 12 rely on, so test 7 uses a second distinct `physicalHostId`.
5. Production transport: `Host: cadence.garden` without `X-Forwarded-Proto` is redirected to https; with `X-Forwarded-Proto: https` it is 200 with `strict-transport-security`.
6. CORS (negative only): an `Origin: https://evil.example` request gets no `access-control-allow-origin` (production default empty list, blank `BL_CORS_ORIGINS` accepted). The allow path stays pinned by the coordinator unit tests.
7. Discovery plane over the published port: join with the join token and a valid body is 200 with credentials; wrong token and no token are 401 (the gateway address, not loopback, reaches the container); `GET /api/discovery/status` with the admin token is 200 and with the join token 401. After the join, `/data-discovery/state.bin` exists in the container and is owned by the same uid as `id -u` of the service user (`stat -c %u`): evidence the BEAM, as the non-root user, wrote into the named volume.
8. Effective release config, via `docker exec … /app/bin/coordinator rpc` printing `Jason.encode!` of non-secret keys only: `discovery_validator` head is `/usr/local/bin/deno` and ends in `check-attempt`, `data_dir` `/data`, `discovery_data_dir` `/data-discovery`, `cors_origins` `[]`, `garden_scheduling` `false`, `allow_local_admin` not true. This proves `runtime.exs` read the packaged environment and is the only proof `allow_local_admin` is off.
9. Validator runs from the image’s cache as the service user (name: `validator runs from the image’s cache`): read the command with `docker exec <c> printenv BL_DISCOVERY_VALIDATOR`, split on spaces as `runtime.exs` does, `docker exec` it with `--manifest/--case/--attempt` pointing at non-JSON files under `/tmp`; expect exit 0 and the `manifest or case is not JSON` verdict. A second run under the same `--cached-only --lock --frozen --config` flags uses `deno eval` to import `file:///opt/browser-life/tools/lib/discovery-pin.ts` and call `verifyPin('/opt/browser-life')`, expecting `ok`: this covers hash verification of the vendored renewal copy, `PIN.json` and the pin helper. A third run, as the service user with the image's own `DENO_DIR`, executes the pinned code the way `pinCall` does: `deno run --allow-read --config=…/vendor/construction-renewal-v1/deno.json --no-lock --no-remote --no-npm tools/discovery-pin-case.ts freeze-check` with `{"cases":[]}` on stdin must exit 0 and print `{"checks":[]}`, so a missing COPY or a broken import map fails under the same named assertion. Not proven: a real campaign verdict (that stays in `tests/deno/coordinator_integration.ts`).
10. Non-root and writable volumes (name: `runs as the unprivileged coordinator user`): `id -u` is not 0 and the user name is `coordinator`; that user can create and remove a file in `/data` and `/data-discovery`. (The earlier `/app has no data*` check is dropped as vacuous; the `/app` crash-loop is pinned by the relative-directory refusal in C6.)
11. Clean stop: `docker stop -t <compose stop_grace_period>` returns within the bound and `ExitCode` is 0 (a release started with `start` execs the BEAM, which exits 0 on SIGTERM); anything else, 137 and 143 included, is a failure, and the observed value is recorded after the first run.
12. Restart with state (last test): start a second container on the same two labelled volumes with the same environment, wait for readiness, and assert admin `GET /api/discovery/status` still reports the worker joined in test 4 or 7. Proves state round-trips through the non-root user’s volumes across a graceful stop and exercises the `Discovery.init` read path.

**Join-token control (one extra labelled start, outside the deployed suite):** a container started without `BL_DISCOVERY_JOIN_TOKEN` (which the compose guard prevents in deployment) must still answer 401 to a join over the published port (asserted). The unauthenticated in-container joins via `127.0.0.1` and `[::1]` are printed with `console.info`, not asserted, because of the dual-stack mapping above; the first hosted run settles what the image does and the notes are then updated from that evidence.

**C6. Refusal matrix** (describe "refuses to start", each case is the C3 environment with one change, run detached with the same labels, `docker wait` bounded to 90 s): the healthy start in C5 is the positive control, so each refusal is attributable to its one change. Pass criteria per case: container exits non-zero, `State.Running` false, no host port ever answered (published port closed), logs (stdout+stderr) contain the named message, and logs contain none of the generated secrets.

| Case | Change | Message expected |
| --- | --- | --- |
| missing admin token | `BL_ADMIN_TOKEN` removed; again set to `""` | `BL_ADMIN_TOKEN must be set in production` |
| missing key base | `SECRET_KEY_BASE` removed | `SECRET_KEY_BASE is missing` |
| wildcard CORS | `BL_CORS_ORIGINS=*` | `BL_CORS_ORIGINS` and `is not allowed in production` |
| plain-http CORS | `BL_CORS_ORIGINS=http://example.org` | same |
| bad count | `BL_MAX_ISLANDS=lots` | `BL_MAX_ISLANDS: "lots" is not a positive whole number` |
| bad switch | `BL_GARDEN_SCHEDULING=maybe` | `BL_GARDEN_SCHEDULING must be on or off` |
| relative discovery dir | `BL_DISCOVERY_DATA_DIR=data-discovery` (resolves under read-only `/app`, the original crash loop) | a permission error (`eacces`/`permission denied`; exact text settled on the first run), non-zero exit, nothing written to the container layer |
| discovery inside data | `BL_DISCOVERY_DATA_DIR=/data/discovery` | `overlaps the registered queue's` |
| discovery equals data | `BL_DISCOVERY_DATA_DIR=/data` | same |

Each case uses its own scratch volumes (or none: the failure precedes any state) and is removed in the same cleanup path. The missing-join-token case is deliberately **not** in the matrix (Grounding); it is the C5 control.

**C7. Two canaries, each failing one named assertion** (mirroring PR89’s packaging and content pair). Disposable images are built `FROM` the **tag** from C2 (`FROM bl-coordinator-image:$RUN`), never `FROM sha256:<id>`, which BuildKit parses as a registry reference and fails to resolve; the canary Dockerfiles are written inline in the workflow with the tag (a separate `from` verifier was dropped as unable to fail). Each canary is built with its own `--iidfile` and the **ID** from that file, not a tag, is passed as `BL_COORDINATOR_IMAGE`. (a) `cache`: `USER root`, `RUN rm -rf /opt/browser-life/.deno`, `USER coordinator`, which still boots and passes everything except test 9 (tests 1-8 and 10-12 probe with `DENO_DIR=/tmp/deno-probe` and do not depend on the cache); (b) `root`: `USER root`, which passes everything except test 10. Each run executes only the healthy-start suite (`-t "started as deployed"`, refusal matrix excluded) and must exit exactly 1; Vitest JSON must contain exactly one failed test whose full name and message include the expected strings; JUnit must report `failures="1"`, `errors="0"`, no `<error>` element (PR89 D16). The two verifiers become one small script, `tools/ci/verify-image-gate.mjs` (subcommands `gate` and `canary`), rather than inline heredocs, so they are unit-tested locally with fixture reports (C10). A canary that exits 0, exits 2, fails a different test, or fails two tests must fail the job.

**C8. Cleanup scoped by labels and fail-loud.** Every container and volume the test creates carries `bl.coordinator-image.invocation=<id>` (plus `bl.coordinator-image.ci=<run>` in CI) and a random-suffixed name. Names are recorded before the creating command so a timed-out CLI still leaves a candidate, but a recorded name is only a candidate: deletion happens only after a successful label-filtered enumeration (`docker ps -aq --filter label=…`, `volume ls -q --filter label=…`) returns the resource ID, and removal is by those IDs, so a create that failed on an existing unlabelled resource never deletes it. Containers (`rm -f -v`) go before volumes. Enumeration failure counts as unconfirmed (an inspect exit 1 is never "absent"; only a successful label listing confirms absence), survivors throw from `afterAll`, scratch is deleted only after confirmation, logs are dumped (redacted) before removal. A fault probe (C10) creates an unlabelled resource under a recorded name and verifies it survives. The workflow’s final `if: always()` step copies PR89’s: bounded `docker ps -aq` and `volume ls -q`, filtered on `label=bl.coordinator-image.ci=$RUN`, remove, re-list, nonzero if anything remains or any query failed, scratch retained when unconfirmed. The pre-cleanup step prints the failure reports. Built and canary images keep the CI label but are not removed (hosted runner disposal is the boundary, as in PR89); stated in the README.

**C9. Gate report floor.** After the main vitest run (`tools/test/coordinator-image.test.ts` only, JSON reporter), `verify-image-gate.mjs gate` requires the suite to have a passed test, `numFailedTests`, `numPendingTests` and `numTodoTests` all 0, exactly the suite's size: at least 13 passed tests whose names contain `started as deployed` and at least 10 whose names contain `refuses to start` (raise the floors with the suite), so a skipped or empty live suite cannot be green.

## Explicit boundaries

No change to physics, rules, `RULE_VERSION`, golden-hash pins, preregistration, coordinator Elixir code or config, `Dockerfile.coordinator`, `compose.dokploy.yaml`, `site-image.yml` or the site test, the `ci-deploy` bookmark, or any deployment, and no public opening. No publishing of images, no secrets beyond values generated inside the run, no Docker daemon assumed locally. Not proven by this gate: Traefik/Caddy topology in front of the coordinator, TLS, the live host and its volumes, real TLS client addresses, a real campaign accepted through the validator, multi-minute stability, and load behaviour (restart-with-state across one graceful stop is proven by test 12). Local no-daemon results are code and configuration proof only; hosted Linux results are the image evidence, and the two are recorded separately.

# Dawn predictions: rules written before the code (2026-10-18)

Slice 29 of the backlog run builds the games row of the shared garden brainstorm
(`docs/shared-garden-brainstorm-2026-10-09.md` §4, "dawn predictions (which lineage holds the field
tomorrow) with free receipts"). The coordinator publishes, for each verified day, who held the field
at that day's end, computed only from files a second island regenerated byte for byte. The page lets a
visitor guess, before the next day is released, which of today's three biggest lineages will hold the
most of the field at the next day's end, or whether the rest will, and keeps the guess on the device
with a receipt. When the next day is verified, the page checks the receipt against public data.

This note was written before any code. It adds no physics, no golden pin, no config key and no route,
and the contract stays `garden-v1` (added keys only). A change to anything below is a dated amendment
at the end, never a silent edit.

## 0. Nothing about a prediction reaches a server

There is no route for predictions and the page sends none. A guess and its receipt live in the
visitor's browser storage and nowhere else. So there is nothing to win, nothing to rank and nothing to
cheat: a receipt proves nothing to anyone but its holder, who could edit it. It is a free receipt in
the brainstorm's sense, a note to self that public data can later check. The page says so in those
words.

## 1. What "a lineage" is here, and why the game counts lines

A census lineage is a lineage key `hi:lo` (`packages/schema/src/layout.ts`: `hi` is the birth step
plus one, 0 for founders; `lo` is the birth cell, the founder index plus one for founders). Every
mutation mints a new key, so a key is one mutation-free line, not a species or a family.

Measured before choosing (local data, read only: `runs/garden-storm/*/treatment/seed-*`, the big storm
at start nutrient 32, 48 and 64, census every 1,000 steps; a "day" taken as 131,000 steps, the census
step nearest the commons' 131,072; 30 consecutive day pairs from the six histories that live past
262,000 steps: five histories, six pairs each). Context for the rule, not a result:

- The biggest key at a day's end holds 1% to 49% of living cells (late in the start-nutrient-48
  histories, 1% to 3%).
- The next day's biggest key was **never** one of the previous day's three biggest keys (0 of 30).
  Read literally ("which of today's top lineages leads tomorrow", by exact key), the answer is "someone
  new" or "no clear leader" every dawn, so that game has nothing to guess.
- Counting each of the three with its descendants born during the two days (§4): the rest together
  held the most cells 19 times, the first 7, the second 3, the third once. Walking the full ancestry
  instead gives the same 30 outcomes; walking only the next day's mutations gives the rest 27 times.

So the game asks about **lines**: a key together with the keys descended from it. The per-day block
still lists exact keys (that is what the census counts), and the page says that a lineage's line
includes its mutants.

## 2. Where the numbers come from (the sound path)

- **Files, not the summary.** A day's census in the view today is the producer's summary, which a
  replay does not check ("reported by the island that ran the day"). `Queue.complete` does not keep a
  verify attempt's summary, so checking summary fields would need a Queue, Segment and runner change.
  Instead the numbers come from two bundle files the producer uploads and the coordinator already
  stores by SHA-256: `lineages.tsv` (`step`, `lineage`, `cells`) and `mutations.tsv` (`childHi`,
  `childLo`, `parentHi`, `parentLo`). Both are in `VERIFIED_FILES`.
- **The gate.** A day's numbers are used only when the day is verified **and**
  `Segment.current_observations/1` is `"match"`: the verifying island regenerated every observation
  file and its SHA-256s equal the producer's uploads, for the run attempt now accepted. Then the bytes
  the coordinator parses are bytes a second island produced independently. A verified day without the
  match (an island that reports no digests, or a mismatch) gets no numbers, and says so.
- **Not the checkpoint.** The checkpoint's digest is the stronger check and it holds the lineage
  words, but the lines need parent links that only `mutations.tsv` carries, so the files are needed
  anyway; one gate for both is simpler than two, and decoding genome channels in Elixir would copy the
  schema's layout into a second language.
- **The producer summary is not changed** and `packages/runner` is not touched.
- **When.** At the moment a day becomes verified with the match, the Queue records the day's block as
  `pending` and starts an unlinked task that streams the files from the store and sends the result
  back. Each start carries a fresh reference kept in the day's `pending` record; the Queue keeps a
  reply only if its reference is the day's current one and the day's accepted run attempt is still
  the one the task read, so a late reply (after a restart, a second start, or a replaced Queue) is
  dropped. Parsing never holds up an island's `/api/next`. Every file or parse error inside the task
  becomes `unreadable`; the task never raises. On start, the Queue looks at every verified day with no
  block or a `pending` one (a day verified before this code, or a crash between the verification and
  the reply), applies the gate, and records `unchecked` or starts the task again.
- **Defensive parsing.** The files are producer-written: a header must match exactly; a row must be
  integers and a key `^\d+:\d+$` with both parts below 2^32; cells positive; no key twice at one step;
  the end step's cells at most the world's cells. Anything else makes the block `unreadable`. Only the
  rows at the day's end step are kept (rows are in step order, so memory is one census).

## 3. The day's block (exact keys)

- **The census** is the rows of the day's `lineages.tsv` at exactly the day's end step
  `(d + 1) * stepsPerDay` (a census step: `stepsPerDay` is a multiple of `censusEvery`, and the
  runner censuses every `censusEvery` steps from the segment's start; every bundle in
  `runs/garden-storm` ends with rows at its final step, and the e2e test checks it on a garden day).
  `livingCells` is the sum of
  their cells (every cell with a lineage key, film included), `lineages` the number of rows. No rows
  means nothing living (`livingCells` 0).
- **Top three** by cells, ties broken by birth: smaller `hi` first, then smaller `lo` (the lab's
  `lineageKeyOrder`). Each with `cells` and `share` (cells over `livingCells`, rounded to 4 places;
  the page words shares from the counts).
- **A clear leader** (rule `lines-v1`): the biggest key, if it holds at least 10% of living cells and
  strictly more cells than the second; otherwise "no clear leader". 10% because in the data above a
  key at 1% to 3% does not hold anything; in the data above 11 of 35 day ends had a key at 10% or
  more, so both words occur. It is a word on the page, not the game's outcome.
- **Labels** are a pure function of the key and the world's width, made by the coordinator: `hi` 0
  reads `founder <lo>`; otherwise `born step <hi - 1> at <lo mod width>,<lo div width>`, or
  `born step <hi - 1>, cell <lo>` when `lo` is not a cell index of the world. Unique because the key
  is. Family names (`packages/metrics/src/families.ts`) are not used: they name clades by history,
  and a second word list in Elixir would drift. Receipts hold keys, never labels.

## 4. The lines into a day (the game's outcome)

For a day *T* ≥ 1 whose block is `ok`, and whose previous day *B = T - 1* is verified with an `ok`
block of its own:

- **Walk.** Each key alive at *T*'s end is traced to its parents through the mutations born on days
  *B* and *T* (both days' `mutations.tsv`), stopping at the first of *B*'s top-three keys it meets, or
  at a key born before *B* began (`hi ≤ B`'s start step). A key that needs a parent neither file holds
  makes the block's lines `unreadable`.
- **Groups.** Each of *B*'s top three (in *B*'s order) gets the cells of the keys whose walk stopped at
  it, the nearest one when one of the three descends from another; every other cell is "the rest".
  Each group carries `cells` and `share` of *T*'s living cells.
- **Who held the field** on day *T*: the group with the most cells, if strictly more than every other
  group; "the rest" can win. A tie, or no living cell, means no group held it.
- **Day 0** has no lines (no day before it). When *B*'s block is not `ok` (pending, unchecked,
  unreadable), *T*'s lines are absent; they are computed again when *B*'s block arrives.

## 5. When a guess can be made (the window and the cut-off)

- **The basis** is the newest released day *B*, and the guess is about day *T = B + 1*. A guess can be
  made only while *B* is verified with an `ok` block that has at least one living cell, *T* is not
  released, *T* is before the horizon, and the garden is neither stopped nor finished. The page reads
  all of it from the view: *B* from `clock.releasedStep`, *T* not released by definition.
- **The cut-off** is *T*'s release: the moment a day is released it is handed to an island
  (the README's release rule: one day per dawn, and only when an island asks), and `days[].releasedAt`
  records it. Predictions close then. "Assigned to an island" has no public time, so it is not the rule.
- **Strictly verified.** The basis must be verified, not merely done: a day is released when its
  predecessor is done, so if the replay lags past the next release the window never opens for that
  day. That is the price of using checked numbers only; the page says "predictions open when the
  newest day is verified and the next is not yet released" when the window is shut for that reason,
  and "day *B* is verified; its files are still being counted" while its block is `pending`.
- **The view's time.** A guess is stamped with the view's `now` (the coordinator's clock), never the
  device's. A view can be up to the cache period (2 s) old, so a guess made against a view from just
  before the release is still before it.
- **Changing one's mind.** A new guess for the same *T* replaces the device's earlier one while the
  window is open. At most 32 receipts are kept per garden, newest first.

## 6. The receipt

Kept under `cadence-garden-predictions:<coordinator>:<garden>` (the visit record's conventions; every
read and write in try/catch; the page works without storage and then says no receipt can be kept):

    {v: 1, garden, createdAt, madeAt, basis: {day, digest, step, livingCells, top: [[key, cells], ...]},
     target, releasedStep, choice, hash}

- `choice` is one of the basis's top keys or `"rest"`.
- `hash` is the SHA-256 (hex, `crypto.subtle`) of the canonical JSON (keys sorted, no spaces) of
  `{v, garden, createdAt, madeAt, basis, target, releasedStep}`: the part of the view the guess was made
  against. The choice is beside it, not inside it. Without `crypto.subtle` no receipt is made, and the
  page says why. The page shows the first 12 hex digits.

## 7. Checking a receipt

Every reading checks the receipts of this planting (`createdAt` equal) against the view, in this
order; the first that applies is the answer:

| Case | Words |
| --- | --- |
| planted again (`createdAt` differs) | not shown (a receipt from an earlier planting) |
| *T* or *B* no longer listed (`days` holds the newest 14) | Cannot be checked here: day *d* is older than the 14 days this garden lists. |
| recomputed hash from the listed day *B* differs | Does not match the garden's record of day *B*. |
| *T* released at or before `madeAt` | Made after day *T* was released; not counted. |
| *T* diverged or failed | Day *T* did not replay the same (or could not run); nothing to check. |
| *T* not verified, or its block pending | Waiting: day *T* is not verified yet. |
| *T*'s block unchecked or unreadable, or its lines absent or not from *B* | Cannot be checked: the replay did not check day *T*'s files. |
| choice is who held the field | Held: *who* held *share* of the field at day *T*'s end. |
| otherwise | Did not hold: *who* held *share* (or: no group held the field). |

## 8. Contract additions (`garden-v1`, added keys only)

- `leadersRule`: `{name: "lines-v1", top: 3, clearLeaderPercent: 10}`, always present.
- `days[].leaders`: `null` until the day is verified; then
  `{status, census, lines}` with `status` one of `"ok"`, `"pending"`, `"unchecked"`, `"unreadable"`;
  `census` (`null` unless ok): `{step, livingCells, lineages, top: [{key, label, cells, share}],
  clearLeader}` (`clearLeader` a key or `null`); `lines` (`null` unless ok and computable):
  `{fromDay, groups: [{key, label, cells, share}], rest: {cells, share}, winner}` (`winner` a key,
  `"rest"`, or `null`).
- A view without these keys (a coordinator from before) shows no prediction panel; the old page
  ignores them.

## 9. Pass criteria (each a named test)

- ExUnit, pure (`garden_leaders_test.exs`): only the end step's rows are kept when earlier steps have
  more rows; the tie order; the 10% boundary (exactly 10% leads, one cell less does not; a tie for the
  top does not); nothing living; labels (founder, a cell, a non-cell `lo`); each malformed input is
  `unreadable` (header, a non-integer, a bad key, a repeated key, too many cells, an orphan child);
  the walk through both days' mutations, stopping at the nearest of the three, and at a key born
  before *B*; groups in *B*'s order; "the rest" winning; a tie; fewer than three in *B*.
- ExUnit, Queue/HTTP (`garden_api_test.exs`, files uploaded through `Queue.publish_file` and the
  verifier reporting digests): a verified day with matching digests gets an `ok` block (after
  `pending`); with a mismatching or missing digest it is `unchecked` (shown failing first); lines into
  day 1 appear whether day 0 or day 1 is verified first; the block survives a Queue restart and a
  `pending` day is finished after one; the view never shows a block for a day that is not verified.
- ExUnit, contract (`garden_contract_test.exs`): the existing drive is unchanged (its files-less
  verified day 0 reads `unchecked`, at the new nullable paths); a second test founds its own garden,
  uploads all six observation files for days 0 and 1, verifies both with matching digests, waits for
  `ok`, and compares `leadersRule` and every day's `leaders` with the fixture's (day 1 with lines, day
  0 with `lines: null`); the `status` enumeration and `winner` are checked.
- vitest (`apps/lab/test/garden.test.ts`): the fixture parses; a view without `leaders` parses with
  the panel off; a malformed block is refused with its path; the window (open, and each reason shut);
  the receipt's canonical text and hash (a fixed vector), independent of key order; each row of §7.
- Playwright (`tests/e2e/public-garden.spec.ts`, mocked contract): at 1280 and 375, an open window, a
  guess, the receipt after a reload, then a mutated view in which day *T* is verified shows "Held" and
  another "Did not hold"; the shut window's reason; a view without `leaders` shows no panel.
- Deno (`tests/deno/garden_e2e.ts`, extended): after day 0 and day 1 are verified on the real GPU,
  `days[0].leaders` is `ok`, its census equals the end-step rows of day 0 in the exported
  `lineages.tsv` (computed by the script), and `days[1].leaders.lines` equals the script's own walk over
  the exported `mutations.tsv`; both are still there after the restart.

## 10. Known limits

- A verified day without the observation match (an older island, or files that disagree) has no
  numbers, and no guess can be made from it or checked against it.
- A replay that lags past the next release shuts the window for that day (§5).
- Receipts older than the 14 listed days cannot be checked on the page.
- "The rest" usually wins in the data above; the page shows the garden's own tally from its listed days
  (how often the rest held the field), not the lab's numbers.
- A receipt is self-kept and editable: it convinces only its holder.

## Amendment 2026-10-18 (during implementation)

Written while the code was built. Nothing above is changed in substance; these fill gaps the text
left open or correct how it would have worked.

1. **One status per block.** When the lines into a day cannot be counted (an orphan key, a
   `mutations.tsv` that does not parse), the whole block is `unreadable`, census included, not only
   its lines. The files of a verified day that disagree with the rule are a fault worth seeing whole.
2. **The task token is an integer, not a reference** (section 2 said "a fresh reference"). The block
   is persisted in `state.bin`, which the Queue decodes with `[:safe]`; a reference names its node, so
   a coordinator restarted under another node name would refuse the file. The token is
   `System.unique_integer/1`; a task answers by `GenServer.cast` to the pid of the Queue that started
   it, so a task from before a restart answers nobody, and inside one Queue a reply is kept only if
   its token is the day's current one and the day's accepted run attempt is the one it read.
3. **When lines are counted again.** Besides section 2's start-up pass (a verified day with no block,
   a `pending` one, or one about another run attempt), a day is counted again, census and lines:
   - when the day before it arrives `ok` and this day is `ok` without lines (section 4);
   - when this day's own answer arrives `ok` without lines although the day before is `ok` by then (the
     two answers crossed);
   - at start, when this day is `ok` without lines and the day before is `ok` (the Queue stopped
     between the two answers).
   Each recount asks for the lines, so the chain ends. While a day is counted again only for its lines
   it keeps its `ok` census in the view (no flicker to `pending`).
4. **Checking a receipt's hash** (section 7, third row): the page recomputes the hash from the listed
   day *B* (its digest, end step, living cells and top three), the receipt's own `madeAt` and target,
   the garden's name and planting, and `releasedStep = (B + 1) · D`. The copy of the basis inside the
   receipt is for reading only. An edited hash or `madeAt` does not match; an edited choice does (it is
   beside the hash, not in it), which is the free receipt's honest limit (section 0).
5. **A target not yet released is waiting** (section 7, second row): "no longer listed" applies only to
   a day older than the listed 14; a *T* beyond the newest released day reads "Waiting: day *T* is not
   verified yet."
6. **The page's field panel** shows the newest listed verified day that has a block: its census words,
   its top three, the lines into it when counted, and the garden's own tally over its listed days.
7. **A basis taken back** (after the first review): when a recount finds a day's files unreadable,
   the next day's lines counted from it are taken back (the next day is counted again, without
   lines), and the view shows a day's lines only while the day they come from is `ok`. A day's own
   `mutations.tsv` must parse even when there is no day before it to walk to.
8. **A guess is made against a fresh reading** (after the first review): pressing the button reads
   the garden again and stamps the receipt with that reading's `now`; if the read fails, or the
   window shut since the last poll, no receipt is made. A kept view can be a whole poll period (60 s)
   old, more than section 5's two seconds.

## Amendment 2026-10-18 (after the second review)

Written after three review lenses and a Codex pass on the built slice. It corrects the note where
it was wrong and records what changed in behaviour; the text above stays as it was written.

1. **Corrections to the text above.**
   - Section 0 says "nothing to cheat". Wrong as worded: the `fork` checkpoint at the end of day *B*
     is public and the physics is exact, so anyone can replay day *T* before it is released and know
     the answer. Read it as: **no prize, and nothing server-side to game**. A receipt still proves
     nothing to anyone but its holder.
   - Section 1 says "the six histories that live past 262,000 steps". The data has five histories (six
     pairs each, 30 pairs); "six" there is a typo.
   - The first amendment says "Nothing above is changed in substance". Its items 1 (a whole block is
     `unreadable`), 7 (a basis taken back) and 8 (a fresh reading, so a view can be a poll period old)
     do change behaviour; they are amendments, not only gaps filled.
2. **Lines, not exact keys, stays the rule.** Codex read the brief as asking about exact keys ("which
   of today's top lineages, or someone new") and called the lines game a substitute. Section 1 is why
   it is not changed: by exact key, the next day's biggest key was never one of the previous day's
   three in 30 of 30 measured dawns, so that game has one answer. Under `lines-v1` a key born on day
   *T* from one of *B*'s three counts for that one's line (it is its mutant). The page names the fourth
   choice "someone else: the rest (every other line)", and its fine print says that a line holds the
   mutants born on the two days, while older ones count with the rest.
3. **Checking a receipt (section 7), rows refined.**
   - Day *B* listed but without an `ok` count for a verified day (being counted again, run again,
     unchecked or unreadable) reads "Cannot be checked now: ..." with the reason, in the pending
     tone. "Does not match the garden's record of day *B*" is kept for a real difference: a hash
     that differs, a target that is not *B + 1*, or lines that are not from *B*.
   - Day *T* `unreadable` reads "Cannot be checked: day *T*'s files could not be read"; `unchecked`
     keeps "the replay did not check day *T*'s files".
   - Day *T* `ok` without lines while *B* is `ok` reads "Waiting: ... the lines into it are still
     being counted" (a recount is on its way, section 4 and the first amendment's item 3).
   - "Held" and "Did not hold" take the day's verification kind, as its chip does: the clean tones
     (`observed`, `negative`) only for a day verified by another device type; otherwise the `note`
     tone, and the words say "replayed here, not yet verified elsewhere" (or "replayed by a second
     island" when the kind is not given).
4. **A guess belongs to one window.** The page notes the window a choice was made in (the planting,
   *B*, *B*'s digest and count). Pressing the button reads the garden again (the first amendment's
   item 8); if that reading shows another window (the target released, or released and already
   verified so guesses are about the day after, a recount, a new planting), no receipt is made, the
   choice is cleared, and the page says so. A new window also clears a choice on any reading.
5. **Receipts this device could not store** wait in the tab; a later guess for the same day that is
   stored replaces the waiting one. The contract's example garden (`?mock=1`) never stores a receipt.
6. **Counting is bounded and watched.** At most two days are counted at once; a day beyond that shows
   `pending` and waits its turn (a first start onto a garden with many verified days). Each task is
   monitored: one that dies without answering leaves its day `unreadable`. An `unreadable` day is
   counted once more at every start of the coordinator (a read error may have been passing).
7. **Not changed:** a day's stored lines do not name the run attempt of the day they came from. A
   requeued day *B* verified again by another island reproduces its files byte for byte (that is what
   the gate checks), so lines counted from the old attempt equal the new ones; a basis that is no
   longer `ok` hides them (the first amendment's item 7). A malformed leaders block still makes the
   page refuse the whole view, as a malformed food block does: a coordinator fault is shown, not
   hidden.

## Amendment 2026-10-18 (after the third review)

A second Codex pass on the fixes. The text above stays as written; these are the changes.

1. **A counting task outlives neither its coordinator nor a restart of it.** Each task has a small
   watcher that kills it if the Queue goes down first, so the bound of two tasks at once (the
   second amendment's item 6) holds across restarts. A task that dies still never takes the Queue
   down. The waiting days are a first-in, first-out queue with a set beside it, so queueing many days
   at a start costs O(n log n), not O(n²).
2. **A receipt this browser cannot check** (no `crypto.subtle`, or the digest refused) reads "Cannot
   be checked in this browser: ...", in the pending tone, not "Does not match": a fingerprint that
   cannot be made is no evidence either way.
3. **Receipts this device could not store** (the second amendment's item 5) show over a stored one
   for the same day only while they are the newer guess; a later guess stored from another tab wins
   and the tab forgets its own.
4. **Words at the threshold.** Whole percents round, so a biggest key just under the clear-leader
   share reads "just under 10%", never "10%", and a tie for the most is named. The rule (section 3) is
   unchanged; only its words.
5. **The page says what the first correction in the second amendment says**: the public fork
   checkpoint and the exact physics let anyone replay the next day before it is released, so a
   receipt is for fun, not proof of foresight.

## Amendment 2026-10-18 (after the fourth review)

A third Codex pass on the fixes. The text above stays as written; this changes the third amendment's
item 3.

1. **Which unstored receipt is later is told by storage, not by clocks.** A receipt this tab could not
   store remembers which stored receipt for that day it replaced (or that there was none). It shows
   over the stored one while storage still holds that same receipt for the day. When storage holds a
   different one, another tab wrote it after this tab's guess, so the stored one is the later guess
   and the tab forgets its own. `madeAt` cannot decide this: two guesses made against one cached
   reading carry the same `madeAt`, and two tabs' clocks need not agree.
2. **Order.** The receipts shown are newest first by `madeAt` across stored and unstored ones (a tie
   keeps this tab's first), and the cap of 32 drops the oldest, never a newer stored receipt.

## Amendment 2026-10-18 (after the fifth review)

A fourth Codex pass on the fixes. The text above stays as written; this changes the fourth amendment's
item 1 (how "the same receipt" is told) and adds two rules.

1. **A guess has a device-only id.** Two guesses against one reading carry the same hash (the hash
   covers the view, not the choice) and the same `madeAt`, so neither can tell them apart. Each new
   receipt gets `id`, 32 random hex characters made on the device. It sits beside the hash, like the
   choice: it is not hashed, so the receipt's hash and section 6 are unchanged, and it never leaves the
   device. An unstored receipt remembers the id of the stored receipt it replaced; a receipt stored
   before ids existed is told by its hash, choice and `madeAt` together.
2. **Storage that cannot be read is unknown, not empty.** When the read just before a guess's write
   fails, the page does not write (a write over a list it could not read would drop the other
   receipts), and the unstored receipt records that what it replaced is unknown. At the first reading
   that works it takes what storage then holds for that day as what it replaced and keeps showing; a
   later stored guess from another tab still wins over it. Known limit: a guess another tab stored
   during the outage loses to this tab's, since nothing records which came first.
3. **The privacy test closes its baseline before any choice.** The Playwright test's list of requests
   allowed later is fixed before a choice is selected, so a request made while choosing (one that could
   carry the choice) is never on it.
4. **Known limit: two tabs writing at once.** A guess reads the stored list and writes it back in one
   synchronous step, with no lock across tabs. Two tabs of one browser submitting in the same instant
   can each write a list without the other's new receipt, and both report it kept. The window is that
   one step, and a lost receipt costs nothing (no prize, nothing kept by a server), so the page takes no
   cross-tab lock for it.

## The cheapest unanswered question

Before building another recovery-selection experiment, inspect the **already evaluated parent–mutant pairs** from foundations test 2. The raw files contain regeneration outcomes that the published Variation gate did not use as a changed trait. A read-only reanalysis can determine whether there is already a candidate improvement worth a fresh, matched assay. This is cheaper and less duplicative than another mutation screen.

Availability verified on 2026-10-24 in this checkout:

- `runs/found-t2/screen/`: 468 JSON units (12 founders × 3 mutation scales × 13 batches), with mutant genome hex, mutation slot/delta, evaluation, and matched parent evaluations.
- `runs/found-t2/confirm/`: 333 JSON units, containing candidate and parent evaluations; `experiments/foundations/t2.json` records 665 confirmed candidates.
- Both raw evaluation types include `regenerated`, `recovered`, `recovery`, survival, light dependence, and `perRep` values. The committed `t2.json` summary omits these recovery counts and the direction of changed traits.
- `runs/found-t5/`: 25 units holding 50 evolved-lineage genomes and their raw evaluations, available if a later design needs low-regeneration starting genomes.

These are gitignored local records, not portable archived evidence by themselves. Before analysis, copy or hash an exact input manifest; validate completeness, identities and parent/mutant slot matching. Do not infer that the directory counts alone establish completeness. This audit agent checked structure and provenance only; the companion [read-only outcome audit](recovery-accessibility-2026-10-24/audit.json) records the parent task's new retrospective reanalysis.

The original screen tested 200 single mutants of each of 12 founders at `mutStep` 24, 8 and 4. The old confirmation selected step-24 mutants for viability plus a change in one of six traits or role; **regeneration was not one of those six traits**. Consequently, a retrospective search over the confirmed subset is biased and a negative result cannot exclude regeneration-improving mutations among the unconfirmed screen candidates. Sources: [test-2 design](/Users/nicholas/develop/browser-life/docs/plan.md:213), [trait list and estimator](/Users/nicholas/develop/browser-life/tools/foundations.ts:135), [screen selection](/Users/nicholas/develop/browser-life/tools/foundations.ts:189), [confirmation and published fields](/Users/nicholas/develop/browser-life/tools/foundations.ts:224).

Pairing matters: the original plan calls for identical seed and tile positions, and the raw screen stores a parent evaluation for each mutant slot. A comparison with the pooled parent reference is not the same as a per-replicate matched comparison. The tracked generating runner was checked during the parent task: `tools/assay.ts` runs separate mutant and parent arrays with the same seed and slot order in both `mutants` and `confirm`; `evaluateBatch` emits `perRep` in tile order. This validates the inspected code path; incomplete historical executable provenance still limits the old records. `evaluateBatch([mutant, parent], ...)` places them in **different** tiles (`t = k * reps + r`); it does not create matched physical/RNG exposures merely by using the same seed. A fresh paired assay should run separate genome arrays occupying the same slots, or an equally explicit equivalent. Keep all planned replicates in the unconditional success denominator; report viability and damage/target eligibility separately. ## The measurement distinctions a plan must preserve

`evaluateBatch` already runs with mutation disabled, including when its caller supplies other world options. `DEFAULT_EVAL` grows a standard inoculum for 3,000 steps and allows 2,000 recovery steps in a 64×64 tile. It contains two different lesion measurements:

1. **Whole-tile recovery:** a fixed central disc lesion followed by a total B+P comparison. `recovery` is capped at 1. `recovered` means at least 90% of pre-lesion tile mass. This can be high when an individual does not regenerate.
2. **Tracked regeneration:** target the largest detected component, wound an edge to cover about 30% of its cells, require a post-lesion remnant no larger than 80% of initial component mass, then track by cell overlap every 50 steps. A surviving tracked ID at least 90% of initial mass after 2,000 steps counts.

Sources: [defaults](/Users/nicholas/develop/browser-life/packages/search/src/evaluate.ts:68), [mutation disabled](/Users/nicholas/develop/browser-life/packages/search/src/evaluate.ts:275), [whole-tile lesion](/Users/nicholas/develop/browser-life/packages/search/src/evaluate.ts:382), [tracked lesion/remnant](/Users/nicholas/develop/browser-life/packages/search/src/evaluate.ts:396), [returned measures](/Users/nicholas/develop/browser-life/packages/search/src/evaluate.ts:502).

The current output merges several failure modes into `regenerated = false`: no countable pre-lesion component; component under four cells; ineffective damage; no retained remnant; loss of tracked identity; and a retained remnant that fails to regrow. The wall screens already encountered assay worlds with living mass but no countable component. A new diagnostic should report these categories separately **without dropping the failed trials from its unconditional denominator**. Also record the actual damage fraction: the operational 30%-area target has an explicit minimum-mass-damage check, not an exact 30%-mass lesion.

The existing tracker is an operational observer, not proof of material continuity or reproduction. Earlier reset work found parent attribution inadequate and a conservative material-retention observer too uninformative for its planned contact experiment. Sources: [reset sequencing and outcome](/Users/nicholas/develop/browser-life/docs/plan.md:145), [wall assay mismatch](/Users/nicholas/develop/browser-life/docs/sandbox-cells.md:619), [tracker overlap mechanics](/Users/nicholas/develop/browser-life/packages/metrics/src/tracker.ts:94). A small genotype assay can establish a genotype-dependent change in this operational regeneration measurement; it must not call that endogenous reproduction.

## Recommended first decision, and what it can establish

1. Audit the complete existing test-2 pairs and assay provenance without new GPU work. Label this a retrospective candidate search, not a new confirmation. Report no-ops, viable and nonviable pairs, both recovery measures, ceiling/headroom, and how confirmation candidates were originally selected.
2. If an informative candidate exists, freeze one pair and a fresh matched mutation-off assay before its outputs are observed. Match physical initialization, RNG seed, tile location, lineage identity and all settings except the genome. Resolve genome bytes and the one-step mutation from the existing source files; never rely on summary labels alone. Instrument the failure categories above and use matched undamaged behavior to expose generic growth advantages.
3. A replicated increase establishes a local accessible functional improvement under the assay. It does not prove the world will select that improvement, nor that recovery is open-ended. Only then design a recovery-specific selection experiment.
4. If the retrospective scan is uninformative because founders sit at the ceiling, do not increase its sample size indefinitely. A separately fixed low-regeneration-parent test is a different question; choose a viable evolved genome by an explicit rule, validate assay headroom, and bound the new mutation neighborhood before beginning. A one-parent negative result is local, not proof the substrate cannot improve.

The scientifically new contrast is **directly measured recovery gains in matched inherited variants, followed by selection on those gains**. Re-running random wounds, general pond selection, founder existence checks, or the old whole-world screens does not supply that contrast.

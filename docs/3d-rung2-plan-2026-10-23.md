# Rung 2 plan: the jar (2026-10-23)

Rung 2 of `docs/3d-brainstorm-2026-10-22.md` §5: a 64³ volume, the 3D renderer, and the 3D census, judged
on the stratification readout of rung 1b. This note fixes the design, the check's open parameters and the
order of work before any rung 2 code or run exists.

**Contingent on rung 1b.** Rung 2 starts only if rung 1b's check (M6 in `docs/3d-rung1b-plan-2026-10-23.md`)
says go. If rung 1b pauses (for example M4 finds no qualifying setting, or the check's decision is pause),
this note stays a plan and nothing below runs. Nothing here assumes a particular rung 1b pick: the jar is
calibrated on its own (§5.3).

Code references are to `claude/3d-rung1b-slab` at `3ebbd327` and `claude/3d-volume-view` at `03085047`.

## 1. What the jar is

- **Grid.** 64 × 64 × 64: one tile, `tileW = tileH = tileD = 64`, 262,144 cells (half the slab's 524,288).
  z is closed (layer 0 is the surface, layer 63 the floor), as in the slab.
- **x and y still wrap.** The jar uses the slab rule line unchanged. A walled jar (closed x and y) would be a
  new rule variant with its own neighbour handling, transport walls and golden cases; it is not needed to ask
  the stratification question, so it is deferred. The renderer draws a square glass tank; a cylinder clip
  would be cosmetic only, and would hide wrapped matter, so it is off by default.
- **Light** falls on layer 0 and is shaded layer by layer exactly as in the slab (`lightK`,
  `T(m) = floor(256 · lightK / (lightK + m))`). For the check: `uniform`, `lightBase 40`, `lightAmp 200`,
  seasons off, as in rung 1b.
- **Out of scope** (the slab's exclusions all stay): walls in x and y, lesions as spheres, feeding and
  picking with a 3D cursor, the main lab and garden integration (`sim.worker.ts`, `execution.ts`, OPFS
  checkpoints, replay), phones, the genome table, 96³ and up, three.js, and the second (compartment) check.
  The brainstorm allows the compartment check only after a dated note fixes its definitions before any rung 2
  run; this note does not write it, so **rung 2 is judged on stratification alone**.

## 3. Bounds at 64³

The slab table (`docs/3d-rung1b-plan-2026-10-23.md` §4, `docs/rules.md` slab section) holds unchanged: every
bound there is per cell or per neighbourhood, not per depth. The ones that touch D:

- Cell count 2^18; lineage `LIN_LO` and cell indices fit as in the slab.
- The light pass walks 64 layers per column instead of 8; `L ≤ 255` and the products `< 2^25` per layer do
  not grow with D.
- Memory: the simulator's per-cell storage is 117 words (cells 2 × 7, genomes 2 × 49, U, displacement,
  light, 2 role words), 117 MiB at 64³, before events, ledger, staging and the renderer's own buffers
  (the pack's `word` and light buffers, 2 MiB, and two 1 MiB textures). The largest single buffer (one genome
  copy, 262,144 × 49 words) is 49 MiB, under WebGPU's default 128 MiB binding limit.

**A property of the light rule at depth (not a bug, recorded so nobody rediscovers it).** `L · T >> 8` with
`T ≤ 255` loses at least one unit per layer whenever the cell above holds any biomass. Over 63 layers a column
with biomass in every layer keeps at most 177 of 240 units (ratio 0.738) whatever `lightK` is. Above about
`lightK = 255 · m` the shading is all truncation. Empty cells (`m = 0`, `T = 256`) lose nothing.

## 4. The renderer

The volume sandbox (`docs/3d-volume-view-2026-10-22.md`) recommended: ray march as the base, the surface skin
on bodies, the three.js stage's look rebuilt without three.js, points as the phone path, slices as the truth
check. Rung 2 takes **ray march + surface skin + slices**. three.js and points are out of scope here
(the stage polish and phones come later).

### 4.1 The pack pass (`packages/sim-gpu/src/pack3d.ts`)

The sandbox's canonical input is the `word` buffer (`apps/lab/src/volume/contract.ts`: 262,144 u32, x
fastest, then y, then z, y up). Its `Bake` pass turns `word` plus a per-voxel light buffer into the `vox` and
`aux` textures every approach reads, and the ray march also reads `word` directly for brick occupancy. So the
jar replaces only the sandbox's producers (the stand-in field and the light scan) and keeps `Bake` and the
approaches:

- **`pack3d`**: one compute pass after each displayed step reads `GpuSim3`'s current `cells`, current genome,
  `light` and `roles` buffers on the same device (no CPU copy) and writes `word` and a light buffer (u32,
  0..255) in the contract's layout.
- **`Bake`** gains one option: take an external light buffer and skip its own column scan. With the option
  off it behaves exactly as today, so `volume.html` is unchanged.

Axes: the contract has y up with the sun at y = 63; the sim has z = 0 at the surface. Sim cell `(x, y, z)`
goes to voxel `(x, 63 − z, y)` (for a world of depth D, `D − 1 − z`; the jar page only packs 64³). The
`word` fields, all integer, every constant fixed in the file:

| field (bits) | value |
|---|---|
| density (0-7) | `min(B + P, 255)` |
| hue (8-15) | `hash(LIN_HI, LIN_LO) & 255` with one fixed integer hash written in the file; 0 where B = 0 |
| role (16-19) | if B = 0 and P > 0: 4 (dead: sediment). Else if all four role counts are 0: 0 (none). Else the argmax of photo, grow, decomp, resp mapped to 1, 2, 3, 5; ties go to the earlier in that order |
| material (20-23) | 0 water where B + P = 0; 1 biomass where B > 0 and B ≥ P; 2 membrane where B > 0 and P > B; 3 waste where B = 0 and P > 0 (sediment) |
| nutrient (24-31) | `min(A >> 2, 255)` |

The light buffer holds the step's `L` (0..255) at the flipped voxel. Every value is an integer, so there is no
rounding question until `Bake` divides by 255.

The contract's role codes become: 0 none, 1 photo, 2 grow (was graze), 3 decomp, 4 dead (sediment, as
before), 5 resp (new). Material codes keep their meaning. `contract.ts`, the slices legend and every consumer
of role or material codes in `apps/lab/src/volume/**` (the bake tints, the points sediment filter, the slices
flags, the surface shader's material shading) are checked and changed together, and the sandbox's stand-in
field is adjusted so `volume.html` keeps drawing what it drew.

### 4.2 The jar page (`apps/lab/jar.html`)

A standalone page with its own loop, like `volume.html`. It never touches `sim.worker.ts` or `execution.ts`.
It creates a `GpuSim3` from a slab preset (`jar-spots`, any seed, settings from the URL hash), steps it,
runs the pack pass and draws through the sandbox's `VolumeSource` contract.

- **Views:** ray march with the surface skin on bodies above a density threshold (the default); slices
  (truth check); a layer peel that hides the top k layers; the sandbox's cut-away and camera presets.
- **Controls:** play and pause, steps per frame, seed, mu, sigma, lightK, seasons on or off (the sun that
  dims). The URL hash carries them so a view can be shared.
- **HUD:** steps per second, fps and 1 % low, GPU stage times (step, pack, draw), living cells, and a depth
  profile: photo share by layer from a role readback once a second (2 MB at 64³; display only).

### 4.3 Renderer checks (fixed now)

- **Pack truth test** (Deno, native WebGPU): a 16 × 16 × 16 world stepped 50 times; the pack pass's `word`
  and light buffers read back must equal, word for word, `packReference` (a pure CPU function in `pack3d.ts`)
  applied to `readState`, `readLight` and the role words of that step. A second part builds cells by hand
  (B = 0 with P > 0, P only, B = P, all role counts zero, ties among roles, saturated counts, light 0 and 255,
  z = 0 and z = D − 1, B + P above 255) and asserts the expected words written out literally in the test,
  so a mapping mistake shared by the CPU and GPU code cannot pass.
- **Sandbox regression** (Playwright): `volume.html` still loads and draws every approach with no GPU errors.
- **Page smoke test** (Playwright, Chrome with WebGPU): `jar.html` loads, steps, draws a frame with non-empty
  pixels, and reports no GPU errors, in each view.
- **Frame budget** (decides only the default steps per frame, never the physics): in Chrome on the M1 Max
  at 1280 × 860, Side camera, live 64³ `jar-spots`, ray march + skin, 4 steps per frame: median fps over 60 s
  at least 30. If it misses, the default drops to 2 steps per frame, then to fewer ray steps, and the result
  is recorded in this note.

## 5. Founders, control, readout and calibration

### 5.1 Founders and the control

- Preset `jar-spots`: 64 × 64 × 64, 8 founders each a ball of radius 3 at a seeded random `(x, y, z)`,
  nutrient 32 in every cell, biomass 64 in the balls. Same per-cell matter and the same number of founding
  lineages as `slab-spots`.
- Founder genome and the `neutral` control exactly as in rung 1b §5.1 (lifted generalist; neutral expresses
  `generalistGenome3`).

### 5.2 Readout

As rung 1b §5.2, with one dated fix:

- **Layer groups (fixed 2026-10-23, before any rung 2 run).** Top = the top quarter of layers, z ∈ 0..15;
  bottom = the bottom quarter, z ∈ 48..63. The brainstorm says the readout is "exactly as in rung 1b", and
  rung 1b's groups (two layers of eight) are the top and bottom quarter. Two layers of 64 would be 3 % of the
  jar each, and the bottom two would often have no activity at all, which makes D undefined rather than
  measuring anything.
- Census every 1,000 steps with roles on every census; the ten censuses ending at step 300,000; photo share,
  D, the bar `m + r` from the neutral seeds, 3/3 go, 0/3 pause, 1-2/3 extend to 6 + 6 and need 5 of 6; an
  undefined neutral D is **pause: control undefined**; an undefined evolving D fails that seed.
- Seeds 1, 2, 3 for both arms, 4, 5, 6 for an extension. Calibration uses 101, 102, 103 and never sees them.
- "Go" on rung 2 means rung 3 (big worlds) is worth starting; "pause" closes the 3D line at rung 2 with a
  write-up.

### 5.3 Calibration (J3)

The slab's `lightK` grid does not carry over: attenuation compounds over 63 layers instead of 7. From the
rung 1b M4 results so far (17 of 180 runs), a carpeted slab has a per-layer light ratio near 0.89 at
`lightK 256`, which corresponds to an attenuation-equivalent `B + P` near 33 per cell; a sparse one is far lower. Running the integer light
rule over 64 layers with that biomass in every layer gives floor-to-surface ratios of 0.088 at `lightK 1024`,
0.21 at 2,048, 0.38 at 4,096 and 0.50 at 8,192 (0.74 at 16,384 and above, the truncation floor of §3). So:

- **Grid:** `mu ∈ {20, 30, 40, 50, 60}` × `sigma ∈ {8, 12, 16, 20}` × `lightK ∈ {1024, 2048, 4096, 8192}`:
  80 settings, 50,000 steps, seeds 101-103, evolving arm only, 240 runs.
- **Qualifies:** all three seeds end with living cells between 1 % and 50 % of all cells, and mean light at
  layer 63 between 5 % and 80 % of mean light at layer 0.
- **Pick:** the highest median over the three seeds of living cells at step 50,000; ties to the larger
  `lightK`, then the larger `sigma`, then the smaller `mu`. If none qualifies, stop and write it up.
- The pick goes in a dated amendment to this note before J4.

## 7. The workflow

`.claude/workflows/3d-rung2-jar.js` builds **J0 and J1 only**. J2 to J4 are hours of GPU time on two
machines and run from the main session, as rung 1b's M3, M4 and M6 did. Run it with
`args: { wt: "<absolute path of the claude/3d-rung2-jar worktree>" }` after the branch exists (§2). Stages:

1. **Preflight.** The worktree has `packages/sim-gpu/src/gpu-sim3.ts`, `apps/lab/src/volume/contract.ts`
   and this note; `pnpm install`; typecheck, test and the Deno golden suite are green before any change.
2. **Build.** J0 and J1 in parallel, each told the other's file set and never to touch it.
3. **Integrate.** `jar.html` at 64³ once `tileD` allows it; all gates; the screenshots for §4.3 saved to
   `docs/3d-rung2-jar/`.
4. **Review.** Codex Sol 6.1 High (read-only) on the whole diff, and an adversarial auditor: pack truth at
   the edges (B = 0, P only, all four roles tied, light 0 and 255, z = 0 and 63), the readout at D = 8 against
   the committed rung 1b behaviour, and the 64³ bounds.
5. **Fix.** Address findings, rerun every gate, and append a review section to this note.

Every building stage returns `ok` and one result per named gate. The workflow stops at the first stage that
fails a gate or returns nothing, and a review that did not run (Codex exited non-zero or returned nothing)
stops it too, so a missing review never reads as "no findings". The Chrome golden gate is
`tests/e2e/golden.spec.ts` (it runs `/selftest.html`).

Agents never commit, push or create branches; the main session commits after its own Codex Sol pass.

## 8. Risks

- **64 layers may be too deep for R = 3 organisms.** A body spans about 7 layers; most of the jar may be a
  dark, empty column. The calibration's light window and the quarter groups are there so the check never
  runs in a world where the bottom quarter is simply dead.
- **The truncation floor (§3) bounds shade from below.** A sparse world loses little light; a carpet loses
  at least 26 %. The calibration window accepts both, but a world can only reach 5 % at the floor with a
  dense, deep canopy.
- **Real voxels are noisier than the sandbox's stand-in field.** The ray march may blur thin bodies and the
  skin may flicker in motion. The page smoke test cannot judge that; looking at a running jar can.
- **The renderer and the physics share one GPU.** Steps per frame and the frame budget trade against each
  other; the check's runs are headless and do not care.

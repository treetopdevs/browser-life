# cadence.garden deployment

The public site is built from `Dockerfile.site` and served by Caddy. Caddy sends `/api/*` to the Phoenix coordinator on the project's Compose network. The droplet's existing Dokploy Traefik terminates HTTPS and routes `cadence.garden` to the `site` service on port 80. The coordinator has no public port. The `/healthz` route checks that the coordinator responds.

## Dokploy UI deployment

1. Create a Docker Compose application from this repository. Use `compose.dokploy.yaml` as its Compose path and the repository root as the build context.
2. Set `SECRET_KEY_BASE` to a newly generated value of at least 64 random bytes, and `BL_ADMIN_TOKEN` and `BL_DISCOVERY_JOIN_TOKEN` to two further separate random values. Keep all three in Dokploy's environment settings, never in Git; Compose refuses to start the coordinator without them. The join token is the discovery plane's research credential: give it only to people running discovery workers, never the admin token.
3. Add a domain for service `site`, port `80`, host `cadence.garden`, HTTPS with a managed certificate. Deploy, then confirm both containers respond before changing DNS. Do not use `deploy/compose.traefik.yaml` when Dokploy manages the domain in its UI.
4. In Namecheap Advanced DNS, replace the parking records with `@ A <droplet IPv4>` and `www CNAME cadence.garden` (or redirect `www` to the apex). Preserve any other records that may have been added since this plan was written. The Namecheap API `setHosts` operation replaces the complete host list.

## Host deployment with Dokploy's Traefik

If the Dokploy UI/API is unavailable, the same images can run as a separate Compose project on the droplet using `compose.dokploy.yaml` plus `deploy/compose.traefik.yaml`. The override connects only the site to Dokploy's attachable `dokploy-network` and gives Traefik the same HTTPS and `www` routing labels it uses for existing applications. This project is managed with Docker Compose on the host and will not appear in the Dokploy UI. Keep its source, `.env`, and volume together under `/opt/browser-life`; permissions on `.env` must be owner-only. Set `BL_IMAGE_TAG` to the deployed Git commit and use `docker compose --env-file .env -f compose.dokploy.yaml -f deploy/compose.traefik.yaml up -d --no-build` after loading the matching images.

## Release checks

- `https://cadence.garden/` shows the public homepage and links to About, How it works, Research, Privacy, Participate, Status, and Lab.
- `https://cadence.garden/api/public/status` and `/healthz` return HTTP 200. `/api/status` remains protected by the coordinator's existing access control.
- The Lab joins the coordinator through same-origin `/api` without browser CORS errors. Verify on desktop and a mobile browser before inviting participants.
- Check the HTTPS certificate, redirects, `robots.txt`, and one completed island session.

### Image gate: the actual site image on Linux

`.github/workflows/site-image.yml` (pull requests, pushes to `main`, manual runs; read-only token, no secrets, nothing pushed or deployed) builds `Dockerfile.site` on a Linux runner with `docker build --pull --iidfile`, tests the image by its `sha256:` ID rather than a tag, and logs the ID with best-effort lookups of the base images' `RepoDigests` (`node:22-alpine` and `caddy:2.10-alpine` are still mutable tags). Two kinds of proof, kept apart:

- **Packaged image, as deployed** (`tools/test/site-image.test.ts`). The image starts with its default command, its embedded `/etc/caddy/Caddyfile` and `/srv`, and nothing mounted over either. A synthetic coordinator, the same image running a tiny Caddyfile, answers on the network alias `coordinator` of a private labelled bridge network; the site's port 80 is published only on an ephemeral `127.0.0.1` port. The test checks that the embedded Caddyfile equals `deploy/Caddyfile`; the packaged root, lab and media files and no `/srv/garden`; every page and the CSS/JS it names; the `/lab` redirect and a world's preview; the complete uncached 404 page (missing paths and assets, `/404.html` by name, conditional and range requests); the private garden routes; `/healthz` reaching `/api/public/status`; the coordinator's own 404 and 503 passing through; a 502 rather than the site's 404 once the coordinator stops; and that a forged `X-Forwarded-For` reaches the coordinator as one valid address the client did not write, with `X-Forwarded-Proto: https`. Requests use loopback HTTP; this does not test TLS transport.
- **Native extracted binary** (`deployment-config.test.ts`, `site-build.test.ts`). The workflow copies `/usr/bin/caddy` out of the built image (`docker create` and `docker cp`) and runs it on the host with `BL_CADDY_BIN`, so the whole forwarding and trust matrix (empty, trusted and untrusted peers, spoofed chains, allowlist validation) runs on the image's own Caddy build. That matrix changes the trust list and the peer address, which the container-network test cannot, and it serves a host build, not the packaged files: it proves the binary and the configuration, the first kind proves the artifact.

The workflow builds two disposable canaries from the tested image: one without `/srv/lab/index.html`, one without `/srv/assets`. Each must fail its specific packaged-content or HTTP-asset assertion; a generic crash is not accepted. These are local CI images, never published. Containers and networks carry per-invocation labels and are removed by name with bounded calls, including after startup failure. A final `always()` step attempts run-labelled cleanup on failure or cancellation and reports query/removal failures. Forced runner termination can prevent that step; hosted runner disposal remains the final boundary. Scratch files are removed only after cleanup is confirmed.

Flags:

| Variable | Meaning |
| --- | --- |
| `BL_SITE_IMAGE` | image ID (`sha256:` and 64 hex digits; a tag is refused). Unset: the image suite skips and no Docker command runs. |
| `BL_REQUIRE_SITE_IMAGE=1` | fail, rather than skip, when the ID is missing or invalid, Docker is unavailable or does not know the image. |
| `BL_REQUIRE_DEPLOY_TOOLS=1` | fail, rather than skip, when Caddy (`site-build`, `deployment-config`) or Docker Compose (`deployment-config`) is missing. |
| `BL_CADDY_BIN` | the Caddy binary for the native tests. |
| `BL_SITE_IMAGE_CI_RUN` | optional extra label value (`bl.site-image.ci`) the CI cleanup step filters on. |

Locally, with a Docker daemon (Docker Desktop is enough for the image suite; the extracted binary is a Linux binary, so the native tests there keep using a host Caddy):

```sh
docker build --pull --file Dockerfile.site --iidfile /tmp/site.iid .
BL_SITE_IMAGE="$(cat /tmp/site.iid)" BL_REQUIRE_SITE_IMAGE=1 pnpm vitest run tools/test/site-image.test.ts
```

On Linux, add `docker create`/`docker cp` of `/usr/bin/caddy` and `BL_CADDY_BIN` plus `BL_REQUIRE_DEPLOY_TOOLS=1` to run the other two suites on the image's Caddy, as the workflow does. This was developed on a host without a Docker daemon: there the image suite was exercised for its guards, cleanup paths and assertions (the latter against a native Caddy 2.10.2 serving a Vite build), not against a built container. The [26 October Linux run](https://github.com/treetopdevs/browser-life/actions/runs/40275386264) has now passed all 53 primary tests with no skips, both expected-failure canaries and cleanup. Exact source/image identities and warnings are in the [review record](../docs/site-image-gate-review-2026-10-26.md). Local no-daemon probes remain distinct from that hosted container evidence.

Not proven by the gate: Traefik topology, TLS, the trusted-proxy address on the live network, a populated allowlist in the container, or anything about the live host; the live-host checks below stay open.

### Client addresses, abuse limits and CORS

Checked locally on 17 October 2026 (`docs/release-checks-2026-10-18.md`) and, for the proxy configuration, with Caddy 2.10.2 on 25 October 2026; the live-host checks below are still open.

- **The chain.** Traefik (TLS) → Caddy (`site`) → Phoenix (`coordinator:4000`). Phoenix's peer is always Caddy. With `BL_TRUST_FORWARDED_FOR=1` it reads the right-most `X-Forwarded-For` entry, and it does not authenticate whoever sent it, so the entry is only as good as Caddy's decision about which peer to believe. `deploy/Caddyfile` makes that decision from `BL_TRUSTED_PROXY_CIDRS` (`servers { trusted_proxies static … ; trusted_proxies_strict ; client_ip_headers X-Forwarded-For }`): a peer outside the list is never believed, so its `X-Forwarded-For` is ignored and the address is the peer's own; a peer inside it is believed, and Caddy takes the right-most address not in the list. Both proxy blocks (`/api/*` and `/healthz`) then replace the header with that one address (`header_up X-Forwarded-For {client_ip}`), so a client's own chain never reaches Phoenix. The default is an empty list: nobody is trusted, every visitor is Traefik's address, and the coordinator behaves as before.
- **Trust contract.** Set `BL_TRUSTED_PROXY_CIDRS` to Traefik's own address as Caddy sees it, as a `/32` (and a `/128` if the network carries IPv6), space-separated. Never a whole network range such as `172.16.0.0/12` or Docker's `private_ranges`: `dokploy-network` also holds every other application Dokploy runs, and any of them inside the list could name any visitor. Find the address with `docker inspect -f '{{range $n, $c := .NetworkSettings.Networks}}{{$n}} {{$c.IPAddress}} {{$c.GlobalIPv6Address}}{{"\n"}}{{end}}' dokploy-traefik` (the container is usually named `dokploy-traefik`) and take the line for `dokploy-network`, the network the site's Traefik label names; the same setup applies in Dokploy and host mode. The address changes when Traefik is recreated (a Dokploy or Traefik upgrade): redo the lookup then. A stale entry fails safe, since Caddy then trusts nobody and every visitor collapses to one address, but that is exactly the global lockout below if a join budget is on. What the contract assumes, and what to check rather than take on trust:
  - Nothing untrusted is attached to `dokploy-network` (`docker network inspect dokploy-network`, in Dokploy mode too, where the UI decides the site's attachments). Containers on a Docker bridge share a layer-2 segment and by default may hold `NET_RAW`, so a hostile one could impersonate Traefik's address. The default Compose network is not an isolation boundary against host administrators (who can reach every container address) or against other containers attached to the same network; it keeps out only containers on other networks. Do not describe it as more than that.
  - The coordinator is attached only to the project's default network, with the site, and has no published port (`docker compose … config` shows no `ports`, and `docker network inspect <project>_default` lists just those two). Anything that could reach `coordinator:4000` directly could write its own address.
  - Traefik's entrypoints do not trust a client's `X-Forwarded-For` (its default). Strict mode would still take the right-most untrusted address, so a Traefik that appended the peer would be handled, but confirm what it sends.
- **Preflight before replacing the site container.** The allowlist is space-separated, **not comma-separated**. A malformed address/CIDR makes Caddy refuse to start, taking both the static site and API proxy down; this differs from a valid but stale address, which collapses visitor budgets. Validate the actual file with the release image and intended environment first (requires a running Docker daemon; run from the repository root, after exporting the intended `BL_TRUSTED_PROXY_CIDRS`):

  ```sh
  # Export the intended BL_TRUSTED_PROXY_CIDRS first; otherwise this checks only the empty default.
  docker run --rm --network none \
    -v "$PWD/deploy/Caddyfile:/etc/caddy/Caddyfile:ro" \
    -e BL_TRUSTED_PROXY_CIDRS caddy:2.10-alpine \
    caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
  ```

- **Consistent settings.** `BL_TRUST_FORWARDED_FOR=1`, a non-empty `BL_TRUSTED_PROXY_CIDRS` and a positive `BL_ISLAND_JOINS_PER_ADDRESS` go together or not at all. A positive join budget without the other two is one global cap that a single script can spend for every volunteer, so production keeps the join budget **off** (`config/prod.exs`) and Compose sets **no default** for it: a blank value leaves that. Joins are still bounded by the island table (below). Setting `BL_TRUST_FORWARDED_FOR=1` also tells the garden's food ask that visitors are no longer one shared address, which is untrue while the list is empty or stale. The garden's letter budget (3 per address per hour) follows the same address.
- **All settings are wired.** `compose.dokploy.yaml` passes `BL_TRUSTED_PROXY_CIDRS` to `site` and `BL_TRUST_FORWARDED_FOR`, `BL_ISLAND_JOINS_PER_ADDRESS`, `BL_MAX_ISLANDS`, `BL_CORS_ORIGINS` and `BL_LEASE_MS` to `coordinator`, in both deployment modes, all blank by default; blank leaves the coordinator's own default (for `BL_CORS_ORIGINS`, production's empty list: no cross-origin callers). Set them in Dokploy's environment or the host `.env`, then check the resolved services with `docker compose --env-file .env -f compose.dokploy.yaml [-f deploy/compose.traefik.yaml] config`. `tools/test/deployment-config.test.ts` checks that resolution and the forwarding behaviour against Caddy, and `BL_REQUIRE_DEPLOY_TOOLS=1` makes it fail rather than skip when Caddy or Docker Compose is missing. The site image runs `caddy:2.10`; the native checks used Caddy 2.10.2 (`BL_CADDY_BIN` points the tests at a binary) with empty and populated lists. The image gate below runs the actual image on Linux; it covers the default (empty-list) start only, so on the host still confirm `docker compose build site` and a start with both an empty and a populated list.
- **Live-host checks (still open; do them in Dokploy mode and in host mode).** Use a temporary `BL_ISLAND_JOINS_PER_ADDRESS=2`, with the three settings above, and restore the intended value afterwards.
  1. *Separate visitors.* Visitor A (one external address) joins until `POST /api/islands` answers 429; visitor B, on a different external address, still joins. Repeat with an IPv6 visitor if the host has an AAAA record.
  2. *Spoofing.* A, already refused, repeats the join with a forged `X-Forwarded-For` (B's address, then two `X-Forwarded-For` headers, then a long chain ending in an unrelated address): still refused, and B's budget is not spent by A.
  3. *Impersonation.* From an unrelated container on `dokploy-network` (`docker run --rm --network dokploy-network curlimages/curl …`), request `http://site/api/public/status` with a forged `X-Forwarded-For`, and try `coordinator:4000` by name and by its address: the name does not resolve, the address does not answer, and joins via `site` are counted against that container's own address, not the forged one. In host mode, also confirm the two projects' containers are on the networks listed above.
  4. *Wrong settings.* With the join budget on and the list emptied, confirm the lockout (one address spends it for all) so it is recognised if a stale entry causes it.
- **Limits that hold regardless of the proxy.** `POST /api/next` is limited per authenticated island to 120 a minute, a hard cap well above the runner's idle poll (one every 5–10 s). The segment routes (heartbeat, complete, reject, fail, uploads, checkpoint downloads, and an island's file downloads, not the administrator's exports) are limited per island to 600 a minute, and an island holds at most 4 pending assignments. Join and next bodies are JSON only and at most 16 KB (an untyped body is read up to 16 KB and dropped). The island table is bounded at 20,000 (`BL_MAX_ISLANDS`): at the bound a join reclaims expired leases and forgets islands that never did work and hold nothing, the longest unseen first but never one seen in the last ten minutes, and otherwise answers 503. `/api/public/status` and `/healthz` are served from a 2 s cache whose misses are coalesced, so a flood of status reads costs the queue about one call per two seconds plus the time to compute it. Only one reader at a time asks the queue: on a cold cache (just after a restart) whose queue is slow, the others answer 503 with `Retry-After: 1` after 2 s, so `/healthz` can briefly be a 503 there; nothing in the deploy probes it automatically.
- **What the island runner does with a 429 or 503.** `packages/runner/src/island-backoff.ts` retries only a 429 or 503 that carries `x-island-request-applied: false` (the coordinator says the operation never happened), at most 4 attempts within a 120 s budget, waiting the longer of `Retry-After` and an exponential backoff (1 s, 2 s, 4 s with up to 25% jitter). The cooldown is shared by all of an island's calls, its heartbeat included. A network failure, any other status, or an unmarked 429/503 is never replayed, because the request may have been applied. When the attempts or budget run out the refusal is returned to the caller.
- **Task lease (`BL_LEASE_MS`).** Milliseconds, a positive whole number; blank keeps the default of 600000 (ten minutes). A run's lease expires after that long without a heartbeat, and the runner heartbeats every 60 s (the first one a minute after the task starts), with the retry budget above on top. So a lease needs room for 60 s plus up to 120 s of retries plus slack: below about three minutes healthy work can be reclaimed, and a development value of a few seconds will reclaim every task before its first heartbeat. Leave it blank in production unless there is a reason, and keep any override well above that.
- **CORS.** Leave `BL_CORS_ORIGINS` unset: the site and `/api` share one origin through Caddy. Production config allows no cross-origin callers by default, and the coordinator refuses to start unless every `BL_CORS_ORIGINS` entry is a whole https origin exactly as a browser sends it (`https://host` or `https://host:port`, lowercase, no `*`, path or trailing slash).
- **Operator views.** `/api/status`, `/api/experiments/<name>` and `/api/discovery/status` need `BL_ADMIN_TOKEN` (tokenless local administration is off in production). Caddy forwards only `/api/*` and `/healthz` to the coordinator, so its `priv/static/index.html` operations page is not reachable at `https://cadence.garden/index.html`; confirm that on the live host.

The named `coordinator_data` volume contains the queue and checkpoints, and `discovery_data` (mounted at `/data-discovery`, set by `BL_DISCOVERY_DATA_DIR`) holds the discovery plane's research state. That directory needs writable, persistent storage separate from `BL_DATA_DIR`: the coordinator refuses to start when it lies inside `BL_DATA_DIR` or cannot be created, and an unwritable one fails at the first write. The coordinator image carries Deno and the validator's source (`tools/discovery.ts check-attempt` with `packages/`, `tools/lib/` and the vendored pin) at the image's commit, set by `BL_DISCOVERY_VALIDATOR`, so the deployed plane validates and accepts uploaded results. Its npm dependency is pinned by `deploy/discovery-validator.lock`, not the repo's `deno.lock` (part of every campaign's source closure); regenerate that lock when `deno.json` changes an npm version, and the image build fails until it matches. Workers join with `deno run -A tools/discovery-worker.ts --coordinator https://cadence.garden --host <machine-id> --token <BL_DISCOVERY_JOIN_TOKEN>`. The validator is the deployed commit's code, while workers run the campaign's frozen source closure, so freeze campaigns for the plane from the deployed commit. Back up both volumes before every deployment that changes data formats and include it in the droplet backup policy. For rollback, redeploy the previous Git revision in Dokploy or select the previous image tag in the host Compose project; restore the matching volume snapshot if the data format changed. Do not destroy the volume when recreating the Compose app.

## Opening the shared garden

The commons is not founded, and `/garden/` stays unlinked and `noindex` until it is. `docs/garden-opening-2026-10-18.md` is the checklist: every decision and step, with its recommended default, its evidence and its status. The deploy-side items are there: the proxy settings above (`BL_GARDEN_ISLAND_TOKEN` is the one setting not yet in `compose.dokploy.yaml`), a full deploy of both images, the volume backup and the rollback levers. The founding is `bin/garden-found --coordinator https://cadence.garden`, which is a dry run that sends nothing. With `--apply --confirm-coordinator https://cadence.garden` it founds the commons with exactly the checklist's parameters, after a typed confirmation. It reads the admin token from `BL_ADMIN_TOKEN` only, never prints it, and reports an existing commons instead of founding again. None of this is done by the scripts here or by CI.

## Site and lab release, garden held private — 19 October 2026

The site image removes `/garden/` from the built files. Caddy returns 404 for
`/garden`, its descendants, and singular/plural garden API routes (public and
keeper routes), before proxying requests. The coordinator remains reachable
only on the private Compose network. Compose sets `BL_GARDEN_SCHEDULING=off`:
no garden day advances at dawn or is assigned for running or verification,
including existing days. Generic segment checkpoint and observation downloads
also refuse garden artifacts while this switch is off. Ordinary experiments
remain eligible. Local development
keeps scheduling enabled unless explicitly disabled. Opening the garden later
requires deliberately changing these release safeguards and completing the
garden-opening checklist; an environment change alone does not publish it.

The gate prints each test invocation ID and captures container logs before cleanup. CI failure reports are printed before scratch removal. Normal test hooks clean up local runs, but forced termination can bypass them; for a killed local run, list containers/networks using the exact printed `bl.site-image.invocation=<id>` label and remove only those resources. The hosted workflow also has a bounded always-run cleanup step scoped to its run label. Failed Docker queries make cleanup fail; they do not count as an empty resource list. Images are retained for inspection (hosted runner disposal removes them); this job is not configured for a persistent self-hosted runner. Base-image digest logging is best-effort, while the tested built image ID is always required.
